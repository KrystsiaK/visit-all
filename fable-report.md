# Visit All — Security & Viability Report

**Дата:** 2026-07-13
**Аналитик:** Claude (Fable 5)
**Ветка:** `codex/auth-deploy-readiness`
**Объём анализа:** 184 TS/TSX-файла, 6 server-action модулей (~6 700 строк), 6 API-роутов, 23 SQL-миграции, next-auth конфигурация, storage/rate-limit/security слои, зависимости (`npm audit`).

---

## 0. TL;DR (краткий вердикт)

**Проект жизнеспособен и его стоит продолжать — но не запускать на реальных пользователей до устранения находок уровня Critical/High.**

Инженерное качество кодовой базы **выше среднего** для проекта такой стадии: запросы к БД параметризованы (SQL-инъекций не найдено), пароли хешируются (scrypt для новых, bcrypt для legacy), rate-limiting реализован на уровне БД, admin-панель защищена RBAC, выставлены security-заголовки (HSTS, CSP, X-Frame-Options). Это фундамент, на котором можно строить бизнес.

Однако есть **1 критичная** и **3 высоких** проблемы, которые сейчас делают продакшн небезопасным:
- Захардкоженный **superadmin-бэкдор** (`demo@visitall.com`), который миграции насильно пересоздают при каждом деплое.
- Две **IDOR-уязвимости в мессенджере** — любой авторизованный пользователь может читать чужую переписку и писать в чужие чаты.
- **Живые production-ключи** (Anthropic, Resend) в рабочем `.env.local`.

Все они устранимы за 1–3 дня. Это не архитектурный тупик, а «недоделанный hardening». **Рекомендация: продолжать, но сначала закрыть блок Critical/High, затем принять стратегическое решение о позиционировании (см. `development-strategy.md`).**

## 2. Детальные находки

### 🔴 C1 — Superadmin-бэкдор, пересоздаваемый миграциями

**Файлы:** `db/migrations/011_seed_demo_account.sql`, `db/migrations/023_admin_telemetry.sql`

Миграция `011` вставляет аккаунт `demo@visitall.com` с фиксированным bcrypt-хешем, зашитым в репозиторий. Ключевая проблема — `ON CONFLICT (email) DO UPDATE`, который **переустанавливает пароль и заново активирует аккаунт при каждом прогоне миграций**:

```sql
ON CONFLICT (email) DO UPDATE
SET password = EXCLUDED.password,
    password_hash = EXCLUDED.password_hash,
    status = 'active',        -- реактивация, даже если админ отключил
    ...
```

Миграция `023` затем **безусловно повышает этот аккаунт до `superadmin`**:

```sql
UPDATE users SET role = 'superadmin' WHERE email = 'demo@visitall.com';
```

Скрипт миграций (`scripts/db-migrate.mjs`) **не содержит гейта по `NODE_ENV`** — то есть в продакшене (README прямо предписывает `npm run db:migrate` при деплое) создаётся постоянный суперадмин с учёткой из системы контроля версий.

**Влияние:** полный контроль над admin-панелью — телеметрия, управление ролями всех пользователей, доступ к данным. Даже если оператор сменит пароль или удалит аккаунт вручную, следующий деплой всё восстановит. README публично рекламирует demo-логин, что привлекает к нему внимание. (Замечание: проверка показала, что хеш **не** соответствует строке `demo` из README — README, вероятно, устарел; но суть не в конкретном пароле, а в самом факте зашитого в VCS суперадмина.)

**Как исправить:**
1. Вынести сидинг demo/superadmin из общего потока миграций в отдельный dev-only seed-скрипт, вызываемый только при `NODE_ENV !== 'production'`.
2. Убрать `status='active'` и `password` из `ON CONFLICT DO UPDATE` (не переустанавливать креды).
3. Первого реального суперадмина создавать одноразовой командой через ENV (`SEED_SUPERADMIN_EMAIL` + сгенерированный пароль), а не хардкодом.
4. Проверить прод-БД на наличие этого аккаунта и деактивировать/сбросить пароль.

### 🟠 H1 / H2 — IDOR в мессенджере (чтение и запись чужих чатов)

**Файл:** `src/modules/messenger/actions.ts`

`getMessages(chatId)` проверяет только факт аутентификации, но **не проверяет, что пользователь — участник чата**:

```ts
export async function getMessages(chatId: string): Promise<Message[]> {
  await getUserId(); // Assert authorized  ← только аутентификация!
  const query = `... FROM messenger_messages m ... WHERE m.chat_id = $1::uuid ...`;
  const { rows } = await pool.query(query, [chatId]);
  ...
}
```

`sendMessage(chatId, ...)` имеет ту же дыру — вставляет сообщение в любой `chat_id` без проверки членства. Так как server actions в Next.js — это фактически POST-эндпоинты, вызываемые напрямую любым авторизованным клиентом, злоумышленник с валидной сессией может:
- **H1:** перебирая/угадывая `chatId` (UUID), читать всю историю личных переписок других пользователей;
- **H2:** отправлять сообщения от своего имени в чужие чаты (спам, фишинг, харассмент, обход приватности).

**Влияние:** это самая опасная категория для социального продукта — прямое раскрытие приватных данных и возможность злоупотребления. Для продукта с перепиской это стоп-фактор для запуска.

**Как исправить:** ввести единый guard, например:

```ts
async function assertChatMembership(chatId: string, userId: string) {
  const { rowCount } = await pool.query(
    `SELECT 1 FROM messenger_participants WHERE chat_id = $1::uuid AND user_id = $2::uuid LIMIT 1`,
    [chatId, userId]
  );
  if (!rowCount) throw new Error("Forbidden");
}
```

и вызывать его в начале `getMessages`, `sendMessage`, `markAsRead`, `toggleReaction`, `editMessage`, `deleteMessage` — везде, где `chatId`/`messageId` приходят от клиента.

### 🟠 H3 — Живые секреты в рабочем дереве

**Файл:** `.env.local`

Файл содержит реальные, рабочие ключи:
- `ANTHROPIC_API_KEY=sk-ant-api03-...` — платный API-ключ;
- `RESEND_API_KEY=re_...` — отправка почты;
- `AUTH_SECRET=...` — секрет подписи сессий;
- `AUTH_DEBUG=true` — логирование событий аутентификации.

**Хорошая новость:** файл **не** закоммичен (`.gitignore` покрывает `.env*`), и `git log` не содержит утечек — это правильно. **Плохая новость:** это боевые ключи, лежащие в открытом виде в dev-окружении и переданные в этой сессии; при любой утечке рабочей папки (бэкап, синхронизация, шаринг экрана, компрометация машины) они скомпрометированы.

**Как исправить:**
1. **Ротировать** `ANTHROPIC_API_KEY` и `RESEND_API_KEY` (они были показаны ассистенту в этой сессии — считать потенциально раскрытыми).
2. Для локальной разработки использовать ключи с ограниченными правами/бюджетом, отличные от прод-ключей.
3. `AUTH_DEBUG` держать `false` вне отладки — он логирует email’ы и попытки входа.
4. В проде хранить секреты только в секрет-менеджере платформы (Railway/Vercel env, а не в файле).

### 🟡 M1 — `updateEntityRating`: нет проверки владельца + глобальный UNIQUE

**Файлы:** `src/app/actions.ts` (`updateEntityRating`), `db/migrations/006_entity_widget_enrichments.sql`

Таблица `entity_ratings` объявлена с `UNIQUE (entity_container_id)` — то есть **одна оценка на контейнер глобально**, а не по пользователю. При этом `updateEntityRating` делает upsert без проверки, что контейнер принадлежит вызывающему:

```ts
INSERT INTO entity_ratings (entity_container_id, user_id, value, updated_at)
VALUES ($1::uuid, $2, $3, NOW())
ON CONFLICT (entity_container_id) DO UPDATE
SET value = EXCLUDED.value, ...
```

Любой авторизованный пользователь, зная `containerId`, может перезаписать оценку чужой сущности. Дополнительно это логическая ошибка: `getEntityRating` фильтрует по `user_id`, ожидая оценку «на пользователя», но схема хранит одну на контейнер — модель данных противоречива.

**Как исправить:** либо (a) сделать `UNIQUE (entity_container_id, user_id)` и хранить оценки по пользователю, либо (b) если рейтинг всё же владельческий — проверять владение контейнером перед upsert (как в `updateEntityInfo`, где используется `getEntityContainerId(client, type, id, userId)`).

### 🟡 M2 — `markAsRead` без проверки участия
Тот же класс, что H1/H2, но ниже по влиянию (правит только флаг `is_read`). Закрывается тем же `assertChatMembership`.

### 🟡 M3 — `/api/ready` раскрывает инфраструктуру
`src/app/api/ready/route.ts` — неаутентифицированный эндпоинт, возвращающий `database.error` (текст ошибки от pg, может содержать хост/имя БД) и список отсутствующих S3-переменных. Полезно для внутреннего мониторинга, но не должно быть публичным. Рекомендация: отдавать наружу только `status: ready|degraded` без деталей, а детальную диагностику — за внутренним токеном/сетью.

### 🟡 M4 — CSP с `'unsafe-inline'` для скриптов
`next.config.ts`: `script-src 'self' 'unsafe-inline'`. Приложение рендерит пользовательский контент через `react-markdown` — при любой ошибке санитайзинга `'unsafe-inline'` снимает главный барьер против XSS. Рекомендация: перейти на nonce-based CSP (Next.js это поддерживает) и убедиться, что `react-markdown` не включает опасные плагины (`rehype-raw`) для пользовательского ввода.

### 🟡 M5 — Спуфинг IP в rate-limit
`getClientIp` берёт первый элемент `X-Forwarded-For`, которым клиент управляет напрямую. Login-лимит частично держится на email (`${email}|${ip}`), поэтому полного обхода нет, но IP-компонент недоверенный. За прокси (Railway/Cloudflare) нужно брать конкретный доверенный заголовок (`cf-connecting-ip`) и/или число хопов.

### 🟢 Low
- **L1** — `npm audit --omit=dev`: 5 moderate в `@opentelemetry/*`. Запустить `npm audit fix`; телеметрия опциональна (`OTEL_ENABLED=false`), риск низкий.
- **L2** — `/api/widget-builder` вызывает Anthropic-стриминг без rate-limit. Любой авторизованный пользователь может генерировать неограниченно — это **cost-DoS** (счёт за токены) и surface для prompt-injection (сообщения идут в Claude как есть). Добавить `assertRateLimit({ scope: "widget_generate", ... })` и лимит длины/числа сообщений.
- **L3** — При отсутствии Resend `password-reset` логирует полный reset-URL в консоль (`console.info`). В проде логи могут агрегироваться — не логировать токены.
- **L4** — `E2E_TEST_MODE=1` целиком отключает rate-limiting (`assertRateLimit` возвращается сразу). Убедиться, что переменная не может попасть в прод-окружение.

## 3. Что сделано хорошо (сильные стороны)

Это важно для бизнес-решения — базовая гигиена безопасности присутствует, значит команда способна довести hardening до конца:

- ✅ **Нет SQL-инъекций.** Все 274 обращения к БД параметризованы (`$1, $2, ...`), конкатенации строк в запросы не найдено.
- ✅ **Хеширование паролей:** scrypt для новых, bcrypt-совместимость для legacy, никаких plaintext-сравнений.
- ✅ **Rate-limiting на уровне БД** с блокировками `FOR UPDATE`, отдельными scope’ами для login/register/verify/reset/upload — грамотно.
- ✅ **RBAC в admin-панели:** `verifyAdminAccess()` проверяет роль по БД на каждом действии; support не может менять роли.
- ✅ **Ownership-проверки в CRUD сущностей:** удаления и апдейты pins/traces/areas/collections консистентно ограничены `AND user_id = $N`.
- ✅ **Security-заголовки:** HSTS, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, базовый CSP.
- ✅ **Валидация ввода:** upload (MIME allowlist + лимит 20 МБ + санитайзинг имени), map-route (строгая проверка координат).
- ✅ **Токены сброса пароля:** `randomBytes` + хранение sha256-хеша + TTL 2 ч — по best practice.
- ✅ **Секреты не в git-истории.**

## 5. Бизнес-вердикт

**Продолжать.** Технический фундамент здоровый, находки — это «недошлифованный hardening», а не системная гнилость. Ни одна из проблем не требует переписывания архитектуры. Реальный стратегический риск проекта лежит **не в безопасности, а в позиционировании продукта** (консьюмерское гео-приложение против dev-фреймворка) — этому посвящён отдельный документ `development-strategy.md`.

Условие продолжения: **не пускать реальных пользователей до закрытия Спринта 0.** IDOR в переписке и суперадмин-бэкдор — это репутационные и юридические (GDPR/приватность) риски, которые нельзя нести в паблик.
